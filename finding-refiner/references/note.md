# Note Rendering Contract

Use this contract only when the authoritative type is `Note`.

## Field order

```text
**Title:** <neutral design, trust, dependency, guarantee-boundary, or operational-condition noun phrase>

**Description:**

<self-contained disclosure>

**Code locations:**

- <repo-relative closed range>
```

Every field is required. A Note has no Impact or Suggestion field; an authoritative conditional consequence remains in Description. If the input contains a substantive remediation request or cannot supply a required field without new substantive work, block under the shared rendering contract rather than deleting or reclassifying content.

## Responsibilities

- **Title** neutrally identifies the subject and its accepted design property, trust relationship, dependency, authority, guarantee boundary, deployment condition, or operational assumption. Use a noun phrase, not a defect allegation, consequence-only headline, quality judgment, or remediation command.
- **Description** first establishes the accepted design or trust context, then preserves the operational assumption and boundary. Include responsibility, guaranteed behavior, non-guaranteed behavior, conditional consequence, and project position only when they are authoritative input content. Bind every consequence to its supplied failed assumption, affected object, modality, and boundary. Preserve the difference between a current fact, an accepted condition, a project plan, and a technical guarantee.
- **Code locations** formats supplied evidence for the disclosed design, authority, dependency, assumption, or guarantee boundary. Apply the shared evidence-location rules without repository inspection or evidentiary reassessment.

Use factual condition language such as `relies on`, `requires`, `is responsible for`, or `does not guarantee` only when it expresses the input's existing relationship. Do not turn an operational requirement into a recommendation through `should`, `recommend`, or `consider`. Do not turn an accepted boundary into an issue through unsupported defect, attacker, or unconditional-impact framing.

The final wording must remain a disclosure of accepted security-relevant context, not an allegation that the current implementation violates an expected property and not a request to change current behavior. If preserving the input requires either framing, block.
